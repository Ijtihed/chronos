Panel 01
Ground Context: What A Character Knows
Every game session starts by building a world. But the player never sees the world — they see the world filtered through one person. This panel shows you both sides: what the system built, and what the character is allowed to know.

Ground context is filtered by archetype and geography — a farmer's world is local, a merchant's world is wider.
Behind the Scenes
The Data Flow
POST /api/run → generate_run(era_config) → rolls a random character from the era's archetype pool → generates 4-6 NPCs with random personality traits → calls local LLM (llama3.1:8b) with prompts/ground_context.md to build the character's initial knowledge → saves the full WorldState to SQLite → returns a PlayerView filtered through the Knowledge Matrix.
What the LLM Sees (ground_context prompt)
The prompt receives: era name, year, region, player's role, archetype, location name, location description, and nearby historical events from the Events DB. It returns structured JSON: era_feel (what the era feels like from this person's position), what_character_knows, local_rumors, material_conditions, recent_events_known, recent_events_unknown. This output is stored on the WorldState and fed into every subsequent NPC prompt.
The Knowledge Matrix
Archetypes are tiered: high (scholar, diplomat, noble, administrator), medium (merchant, soldier, craftsman, sailor), low (farmer, servant, refugee). High-tier characters can know about events 3+ graph hops from their location. Low-tier characters only know about events at their own location. The same WorldState produces radically different PlayerViews depending on who the character is. The gap between the two columns above IS the game.
The Region Knowledge Call
After creating the run, the demo calls GET /api/run/{id}/region/{polity}. This queries the Events DB for historical events in that region, filters them through the Knowledge Matrix (same archetype tiers), and then asks the local LLM to generate a one-sentence character-voice summary. The result: known_facts (events the character can know), rumors (events they've heard about but can't confirm), and ignorance_acknowledged (does the character know they don't know things?).

Behind the Scenes
The Turn Pipeline (7 stages, every turn)
1. simulate_turn() — every NPC at the location acts autonomously before the player. 2. parse_action() — LLM classifies player text into action_type, target, intent, significance (0–1), npc_impacts. 3. apply_action() — update WorldState. 4. Schedule consequences if significance ≥ 0.5. 5. check_death() — can the player die from this? 6. generate_npc_pov() — parallel LLM calls, one per relevant NPC. 7. Save + build response.
What Each NPC's LLM Call Sees
The prompt template (prompts/npc_pov.md) includes: the NPC's name, role, archetype, emotional state, personality traits, relationship to the player, disposition, the player's action and its era-description, ground context (the shared world-state knowledge), and historical context retrieved from the Events DB via keyword search. Each NPC returns a 2-3 sentence first-person perspective and an emotional state update.
Why the Responses Differ
A soldier hears "the Ottoman army crossed the Bosphorus" and thinks about defense, deployment, and survival. A merchant thinks about trade routes closing and prices rising. A priest sees divine punishment or prophecy. The NPC voice system (npc-voice-system.md) enforces authentic, era-appropriate voices — small concerns over big history, vulgarity when contextually accurate, biases that match the character's position. NPCs never speak like narrators or therapists.
Panel 03
Needs System: What's Driving This NPC Right Now
Every NPC has 17 internal need dimensions. They're never shown to the player — but they drive every autonomous decision. When survival drops to critical, the merchant stops trading and starts hoarding. When faith spikes during a plague, the atheist becomes a pilgrim. Behavior isn't scripted. It emerges.

Behind the Scenes
No API Call — Pure Simulation Logic
This panel runs entirely client-side, mirroring the logic in backend/npc_personality.py. In the real game, needs are computed server-side and never sent to the player. The player only sees behavior that emerges from needs — they never see the numbers.
The 17 Dimensions
survival, safety, family, social, trade, profit, power, reputation, honor, duty, loyalty, faith, knowledge, order, community, harvest, stability. Each archetype starts with different base values — a farmer has harvest=70 and knowledge=10, a scholar has the inverse. Personality traits (randomly generated per NPC) add further variation.
Urgency Thresholds
Below 15 = critical (red). The NPC will abandon everything else to address this. Below 30 = urgent (amber). This need shapes most decisions. 30+ = stable (green). Met needs don't drive behavior. The get_dominant_need() function returns the minimum value — the most starved dimension. The get_urgent_needs() function returns all needs below 30, sorted ascending.
How Needs Drive the LLM
In the actual game, the autonomous action prompt (prompts/autonomous_action.md) includes the NPC's top 3 urgent needs by name and value. The LLM generates actions that address those needs. A starving farmer tries to find food. A soldier with critical loyalty organizes a defense. A merchant with urgent trade needs seeks a buyer. The LLM doesn't "decide" to be interesting — the need state constrains it into contextually appropriate behavior.

NPC Autonomy: The World Without You

Behind the Scenes
What Happens Each Tick
POST /api/run/{id}/turn with "I wait and observe silently." The action parser returns is_inaction: true — but simulate_turn() still runs first. For every NPC at the location, the backend calls generate_autonomous_action() via the local LLM. Each NPC decides independently: what to do, who to interact with, whether to travel, and how their mood shifts. These decisions update the WorldState before the player's non-action is processed.
The Autonomous Action Prompt
prompts/autonomous_action.md gives each NPC: their name, role, personality, top 3 urgent needs, emotional state, who else is present, location description, recent events, and ground context. The LLM returns JSON: action (what they do — narrated, not "thinking"), interacts_with (name or null), wants_to_travel, travel_destination, mood_shift. NPCs can and do leave locations, build relationships, and change emotional state without any player involvement.
Why 3 Turns, Not /skip
The /skip endpoint advances the world but only returns a summary. By running 3 individual inaction turns, we get the ambient_activity array from each tick — the detailed list of what every NPC did. That's why you see the activity appearing tick by tick: each one is a separate round-trip to the server where the full simulation runs.
Panel 05
Historical Events: The Events DB Live
Every era is seeded with real historical events before the simulation begins. Hand-curated seed events combined with automated Wikidata discovery and Wikipedia enrichment. No LLM needed for this call — pure database query.
Click an era to load events
1,500+ hand-curated historical events. Every era starts from real history before it diverges.
Behind the Scenes
The API Call
POST /api/run/preview — no LLM call, no run creation. The backend queries historical_events in SQLite: SELECT * WHERE year BETWEEN {era_start - 55} AND {era_start + 5}, filters for civilizational + regional significance, deduplicates by text and year, sorts chronologically, returns up to 6. Response includes both formatted strings (loading_events) and structured objects (loading_events_structured) with year, event, significance, and type.
How the Events DB Was Built
scripts/build_events_db.py builds in three layers. Layer 1: Hand-curated seed events (seeds/*.json) — ~30-40 per era, covering the most important events with accurate dates and classifications. Layer 2: Wikidata SPARQL queries that discover additional events by era, region, and type (wars, epidemics, famines, political events). Layer 3: Wikipedia enrichment — each Wikidata event gets context from the article intro, then LLM classification for significance and type.
Event Schema
Each event has: year, region, event (text), significance (civilizational / regional / local), type (war / epidemic / famine / political / religious / economic / natural_disaster / cultural), affects (list of entities), canonical (true = real history, false = game-generated), wikidata_qid (source linkage).
What These Events Do In the Game
1. Seed the loading screen while character generation runs. 2. Populate the player's confirmed_events and rumors in PlayerView, filtered by the Knowledge Matrix. 3. Serve as the canonical baseline for divergence detection — when you change history in Panel 6, these are the events you're contradicting.
Panel 06
Historical Divergence: When You Change History
The simulation starts from real history. But players can contradict it. When a player action contradicts a canonical event, the system detects the divergence, supersedes the original timeline, and cancels downstream consequences. Alternative history begins.

The system detected a contradiction with canonical history. Downstream consequences were superseded. Alternative history begins.
Behind the Scenes
The Divergence Detection Pipeline
1. parse_action() — LLM scores significance (0–1). A peace negotiation about Constantinople scores 0.7–0.9. 2. If significance ≥ 0.6, _check_historical_divergence() fires. 3. Detection is pure heuristic (no LLM): maps action_type to event_type (negotiate → political), queries canonical events within ±5 years of the current year. 4. For each canonical event, checks if the action's target appears in the event text. 5. If match: records divergence on WorldState.historical_divergences, calls mark_consequence_superseded_mem().
The Consequence Queue
Significant player actions (significance ≥ 0.5) schedule future consequences via ScheduledConsequence objects. Each has: trigger_turn (when it fires), effect_type, effect_payload, source_event_id, and a superseded flag. When a divergence supersedes a canonical event, all unfired consequences linked to that event's ID are cancelled. The consequence queue is how the game makes history feel consequential — actions ripple forward in time.
What the Player Just Did

The original timeline — where the Theodosian Walls are breached and the Byzantine Empire ends — is struck through.
